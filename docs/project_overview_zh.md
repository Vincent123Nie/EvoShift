# EvoShift 项目总览

## 一句话

EvoShift 是一个**不微调模型、不需要 GPU**的 Python Agent 研究框架。它研究的问题是：当任务规则、反馈可靠性或用户偏好发生变化时，Agent 如何安全地更新外部记忆，而不是把一次偶发、错误或恶意反馈直接写进提示词。

核心算法叫 **VERA**（Verified Experience Replay and Adaptation）。模型参数保持冻结；会演化的是有版本、可追溯、可回滚的程序性记忆，以及受限的检索策略。

## 解决的问题

普通的 Agent 记忆通常有两个极端：

- 不更新：新政策或新规则出现后，仍按旧经验回答；
- 直接更新：一次错误反馈也可能污染长期记忆。

EvoShift 把“从反馈学习”拆成受验证的状态迁移，目标是在**适应变化、保护旧能力、控制成本**之间取得可测量的平衡。

## 核心流程

```text
任务 -> 检索已激活记忆 -> 冻结 LLM 作答 -> 环境评分
     -> 评估反馈源/上下文是否可信 -> 生成候选经验
     -> 影子区回放验证 -> 试用期 -> 后续记忆开/关对照审计
     -> 激活、回滚或拒绝
```

1. **预测先于学习**：先用当前状态作答、再看反馈。当前题目的答案和隐藏标签不会进入当前决策，避免标签泄漏。
2. **候选记忆先进入影子区**：失败归因器把经验写成结构化卡片（触发条件、适用范围、操作指令、反例和溯源），但它不能直接生效。
3. **同题配对回放**：在相同样本上比较“原方案”和“加入候选记忆的方案”，同时检查当前规则、受保护旧规则、置信区间和 token 成本。
4. **试用期与未来审计**：回放通过后仅以 probation 状态参与检索；在后续真实交互中再做“只移除这张记忆”的对照。确认有益才激活，出现因果伤害则回滚。
5. **长期治理**：已激活记忆仍持续记录效用；发生可信失败时进行精确版本的 leave-one-out 对照，避免陈旧规则长期占用上下文。

## 关键设计

| 模块 | 设计 | 解决什么风险 |
| --- | --- | --- |
| 记忆检索 | 来源域约束 BM25 + Beta 效用 + UCB 探索 + MMR 多样性 | 无关经验、低效经验和上下文拥挤 |
| 反馈信任 | 源级 Beta 后验，按上下文维护已确认/待确认标签 | 单次冲突、噪声和伪造反馈 |
| 漂移处理 | Page-Hinkley 性能/新颖度报警；只允许白名单策略补丁 | 将局部失败误判为全局规则变化 |
| 安全演化 | 影子状态、配对 replay、probation、未来反事实审计、回滚 | 未验证记忆污染线上行为 |
| 可审计性 | SQLite 状态、不可变运行产物、预算账本、冻结 held-out audit | 实验不可复现或事后挑选结果 |

项目还实现了 OpenAI-compatible `/responses` 客户端、重试/缓存/预算控制、假模型离线测试、公开数据下载与 SHA-256 固定、可恢复 sweep，以及 Static、Self-Refine、Reflexion-style、Replay-only、Full EvoShift 等可比基线。

## 已验证的结果

### 1. 公开 LongMemEval_S：检索有明确提升

在冻结的 12 题、同一 `gpt-5.6`、无缓存确认集上，加入受保护的 BM25/LLM 排名融合（BM25/LLM 权重固定为 `0.4/0.6`）相对 BM25：

| 指标 | BM25 | 选择性融合 | 提升 |
| --- | ---: | ---: | ---: |
| Recall-all@5 | 0.8333 | 0.9167 | +0.0833 |
| NDCG-any@5 | 0.7471 | 0.8958 | +0.1488 |
| NDCG-any@10 | 0.7471 | 0.9047 | +0.1576 |
| MRR | 0.6931 | 0.8917 | +0.1986 |

NDCG-any@10 的配对 bootstrap 95% CI 为 `[+0.0513, +0.2704]`。LLM 只能重排匿名候选，不能添加文档；错误输出、未知/重复 ID 和融合不变量异常都会精确回退到 BM25。该结果只证明**检索机制**有效，不是端到端问答或 LongMemEval SOTA 声明。

### 2. 公开来源的 policy-drift 流：得到可信负结果

用真实 `gpt-5.6` 在 Tau3 retail 派生的规则变化流上，完成了 Static、Reflexion-style、Replay-only 和 Full EvoShift 的同模型运行，并记录能力、安全和 token 开销。当前 Full 配置没有超过 Reflexion-style：它在短流中为了防止单次矛盾反馈过早写入，冷启动和规则切换会更慢。

这个负结果是项目的一部分：它定位了“保守信任门导致适应滞后”的真实瓶颈，而不是将一次小样本结果包装成优势。

### 3. 条件序列证据：机制可达，暂未带来能力增益

为避免不同上下文的反馈互相稀释，实现了 conditional shadow e-process：只在相同 `(domain, source, context)` 家族内将同信号视为正证据、冲突信号视为负证据；无关家族不更新证据。

在 3 个保留 seed 的真实模型确认中，它产生 11 次候选证据跨阈值、跳过 337 次无关更新、零有害激活；但 288 个配对 episode 的最终输出完全一致，整体分数仍为 `0.6632`。原因是 replay 或未来审计在流结束前阻止了候选进入 active。这证明了机制的安全可达性，也诚实说明当前流尚未证明分数提升。

## 工程质量与边界

- 当前主分支质量门：`284 passed`，覆盖率 `84.85%`，Ruff、严格 Mypy、sdist 和 wheel 构建均通过。
- 所有正式实验固定数据版本/哈希、配置、选择规则、随机 seed 和运行产物；sweep 可中断恢复。
- 没有使用隐藏 oracle 标签、答案、policy version 或攻击标记驱动在线更新；这些字段只用于事后评估。
- 这不是大规模多租户线上系统，也不应宣称自进化能力已达到 SOTA。当前最强、可直接写进简历的量化结果是 LongMemEval 的受保护检索提升；自进化部分的价值是完整的验证、回滚和负结果分析闭环。

## 面试时可用的表述

> 我实现了一个 API-only 的自进化记忆 Agent。它不直接相信 LLM 生成的反思或单次反馈，而是把经验放入影子区，用同题 champion/challenger replay、试用期和后续 memory-on/off 反事实审计决定是否生效。系统将隐藏标签和当前反馈隔离于当前决策，并对每次状态变化保存版本、证据和成本。公开 LongMemEval_S 的受保护检索实验把 NDCG-any@10 从 0.7471 提升到 0.9047；在真实 policy-drift 流上我也保留了 Full EvoShift 未胜过 Reflexion 的负结果，并定位到保守信任门带来的适应延迟。
