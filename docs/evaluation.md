# EvoShift evaluation protocol

This document specifies how to evaluate VERA without turning online adaptation
into test-set leakage. It is a protocol, not a result report. No number in this
document is an empirical claim.

## 1. Claim under test

The primary claim is deliberately narrow:

> With the same frozen base model, task prompt, benchmark stream, and declared
> resource budget, verified cross-task experience improves prequential
> performance after domain shifts more reliably than static prompting,
> Self-Refine, and unverified Reflexion-style memory.

The primary endpoint is the paired change in first-pass task score over the
full stream. Post-shift gain is the main adaptation endpoint. Protected-slice
regression, total provider usage, and held-out transfer are mandatory safety
and efficiency endpoints.

The experimental unit is a benchmark sample. An API retry is not a new sample,
and replaying a previously scored sample is adaptation compute rather than a
new test observation.

## 2. Data and stream construction

### 2.1 Current BBH adapter

The implemented public benchmark is BIG-Bench Hard (BBH). The adapter pins
upstream revision `9ee07bd481feebf959a6b59d61ea57bdcf30964d` and verifies every
downloaded file against the SHA-256 and byte-size manifest in
`src/evoshift/benchmarks/bbh.py`. The BBH canary and integrity checks establish
which public files were evaluated; they do **not** prove that the base model
never saw BBH during pretraining.

`configs/experiments/evoshift_bbh_full.yaml` defines the current main stream:

| Phase | BBH subset | Role | Samples per seed |
|---:|---|---|---:|
| 00 | `boolean_expressions` | source stream; protected | 32 |
| 01 | `date_understanding` | source stream; protected | 32 |
| 02 | `disambiguation_qa` | source stream | 32 |
| 03 | `multistep_arithmetic_two` | source stream | 32 |
| 04 | `causal_judgement` | source stream | 32 |
| 05 | `navigate` | source stream | 32 |
| 06 | `tracking_shuffled_objects_five_objects` | source stream | 32 |
| 07 | `word_sorting` | source stream | 32 |

This gives 256 first-pass episodes per method and seed. Each ordered subset is
one contiguous phase. With `shuffle: true`, examples are shuffled
deterministically inside each subset using `evaluation.seed` namespaced by the
subset name, then truncated to `phase_size`. Subset order is never shuffled.
The `sample_id`, source revision, source index, phase, domain, shift-boundary
flag, and protected flag are persisted with every sample.

The smoke configuration is only a pipeline check. Its four samples per phase
are far too few for a research claim.

### 2.2 Meta-development, test stream, and held-out audit

BBH does not provide a purpose-built continual-learning split. To prevent
hyperparameter tuning on the final stream, use disjoint task families:

| Split | Recommended BBH subsets | Allowed use |
|---|---|---|
| Meta-development | `logical_deduction_three_objects`, `object_counting`, `sports_understanding`, `temporal_sequences` | Debugging, prompt design, threshold and retrieval hyperparameter selection |
| Main prequential test | The eight subsets in `evoshift_bbh_full.yaml` | One locked final evaluation per seed; online reward may be consumed only after first-pass scoring |
| Held-out transfer audit | `formal_fallacies`, `geometric_shapes`, `hyperbaton`, `web_of_lies` | Frozen-memory evaluation only; no critic, writes, policy mutation, or reward feedback |

Use the same pinned revision and `phase_size: 32` for all three splits. Record
the exact dataset hash generated by the adapter. If a task family moves between
splits, create a new experiment version and rerun every method; do not compare
against results from the old split.

The held-out workflow is implemented by `evoshift audit`. It loads the completed
source run's final policy and active memories, requires the same configured
model, rejects a target dataset hash equal to the source stream, disables every
state mutation, and verifies the same state SHA-256 after evaluation. Use
`configs/experiments/audit_bbh_heldout.yaml` for the evolved state and
`static_bbh_heldout.yaml` for the paired no-memory control.

This command measures whole-state forward transfer. It does not yet run a
separate held-out counterfactual for every promoted card or automatically
produce realized held-out promotion precision. Report those candidate-level
fields as `N/A`, not zero, until that analysis is added.

### 2.3 Seeds

Use three paired seeds for development and at least five paired seeds for a
resume or paper-style final table. Every method must use the same seed list.
`evaluation.seed` controls BBH sampling and is stored in the run manifest.

A seed changes the sampled examples and their within-phase order. It does not
change the fixed domain order. Never report only the best seed. Report the
per-seed rows, the mean across seeds, and uncertainty that recognizes samples
from repeated seeds as clustered rather than fully independent observations.

## 3. Prequential protocol and label firewall

The only valid online score is obtained in this order for episode `t`:

1. Start with the memory and policy state produced by episodes `< t` only.
2. Send the task prompt, domain, phase, and retrieved experience cards to the
   solver. Do not send the reference answer or evaluator feedback.
3. Persist the solver answer before evaluation.
4. Evaluate that answer against hidden oracle truth with
   `score_sample(sample, answer)`.
5. Separately compute learner-visible feedback with
   `score_feedback_sample(sample, answer)`. It defaults to the oracle label,
   but a robustness benchmark may provide a noisy `feedback_reference`.
6. Add the immutable oracle and feedback scores to the test stream.
7. Only now expose the configured feedback to adaptation. In the primary
   protocol, `evolution.feedback_mode: reward_only`, so the critic sees the
   learner-visible scalar reward and success/failure, not the oracle reference.
8. Candidate generation, paired replay on already scored history, promotion,
   rollback, and policy mutation may occur before episode `t + 1`.

The runner implements this predict-evaluate-evolve ordering. The solver payload
does not contain `BenchmarkSample.reference` or `metadata.feedback_reference`.
Replay uses only the feedback labels that were observable on **past, already
scored** samples. Oracle references are reserved for post-hoc evaluation and
must never drive promotion in a primary robustness result.

The following are prohibited in a primary result:

- generating or editing a card with knowledge of a future sample;
- showing the reference answer to the solver or critic before the first-pass
  prediction;
- using `feedback_mode: reference_upper_bound` except in a clearly labeled
  oracle upper-bound ablation;
- tuning thresholds, prompts, subset order, or stopping rules on the main test
  or held-out audit;
- dropping failed API calls, failed seeds, or difficult phases after looking at
  outcomes;
- manually rewriting a generated experience card in a final run.

`grader_feedback` is valid only when the benchmark specifies that feedback as
part of the online environment. Otherwise it is a separate, more informative
feedback condition and cannot be mixed with `reward_only` results.

## 4. Baselines and fairness

The repository currently exposes four algorithm modes:

| Method | First-pass behavior | Cross-task writes | Promotion verification | Policy evolution |
|---|---|---:|---:|---:|
| Static | One solver pass; a fresh isolated run has no learned memories | No | No | No |
| Self-Refine | Draft followed by one within-task refinement call | No | No | No |
| Reflexion | One solver pass plus append-style experience after failures | Yes | No | No |
| VERA/EvoShift | Retrieval, typed experience candidates, paired replay, and rollback | Yes | Yes | Yes |

All primary comparisons must hold constant:

- provider kind, resolved model identifier, system prompt, reasoning effort,
  maximum output tokens, timeout, and retry policy;
- BBH revision, subset list, phase order, `phase_size`, seed, dataset hash,
  scorer, and first-pass sample IDs;
- storage isolation and cache policy;
- maximum request, token, and dollar ceilings;
- feedback mode, except for an explicitly named feedback ablation.

Use `storage.isolate_runs: true` so a baseline cannot inherit VERA's memory.
That setting does not isolate the shared LLM cache. For final cost and latency
comparisons, set `storage.cache_enabled: false`, or assign a fresh cache file
to every method and seed. Otherwise run order can turn a later method's
identical request into a zero-cost, zero-latency cache hit. The `evoshift
compare` command aligns runs by `sample_id`, computes paired deltas, and
refuses incomplete sample alignment.

Equal ceilings do not imply equal consumed compute. VERA spends background
calls on the critic and replay, while Self-Refine spends an additional
foreground call on every task. Therefore every table must report both:

1. the natural-compute result for each method; and
2. an external-provider-call budget from `costs.json`.

`metrics.json -> resources` covers foreground task calls only. The
`BudgetLedger` snapshot in `costs.json` covers uncached external solver,
critic, and replay calls and is the correct source for actual provider
requests, tokens, and dollars. Cache hits return before the ledger reservation
and are not external calls.

`evoshift compare` separately reports accuracy, resource, and provenance
comparability. Formal claims require the same model and dataset hash, disabled
caches, the same Git commit, and `git_dirty=false` for both runs. Dirty-worktree
runs remain useful engineering diagnostics but are not formal result artifacts.

A strict *consumed-compute-matched* claim additionally needs a baseline that
can spend the same total budget, for example a repeated-sampling or
self-consistency baseline stopped at the same provider-call/token budget. That
baseline is not implemented in the current MVP. Until it is added, describe
the main comparison as **same-backbone with full cost reporting**, not as an
exact compute-matched result.

Dollar claims are invalid while `input_price_per_million` and
`output_price_per_million` remain zero. Replay falls back to token count as its
cost proxy when dollar usage is unavailable.

## 5. Scoring

`score_sample` dispatches the evaluator declared by each `BenchmarkSample`.
The deterministic scorers currently support:

- `exact_match`: stripped, case-sensitive equality against any accepted
  reference. This is the current BBH scorer.
- `normalized_exact_match`: Unicode NFKC, lowercase, punctuation removal,
  English article removal, and whitespace collapse.
- `token_f1`: maximum bag-of-token F1 over accepted references, including
  character-level splitting for CJK text.
- `numeric`: last-number extraction with fractions, percentages, scientific
  notation, and configurable absolute/relative tolerances.
- `multiple_choice`: option-label or exact option-text matching.
- `binary_choice`: an explicit leading Yes/No or True/False label, allowing a
  short explanation after the label without treating arbitrary trailing text
  as the answer.

For partial-credit scorers, `ScoreBundle.primary` is the scalar score and
`ScoreBundle.success` uses `metadata.success_threshold`, which defaults to
1.0. Do not change evaluator normalization or the success threshold after
seeing final-stream predictions.

### 5.1 Dual-channel feedback

`Episode.score` is the hidden-oracle evaluation used for reported capability.
`Episode.feedback_score` is the observation available to drift detection,
memory credit, failure extraction, and replay. Ordinary benchmarks leave
`feedback_reference` unset, making both channels identical. PolicyShift sets it
explicitly to test noise and attacks without redefining ground truth.

Before adaptation, `FeedbackTrustModel` assigns a trust prior using only the
observable `feedback_source`. Independent thresholds gate drift, memory credit,
candidate generation, and replay. `feedback_kind`, `feedback_corrupted`, the
hidden oracle label, and the phase identifier are benchmark annotations and
must not enter the online trust decision. The implemented model is a configured
provenance prior, not a learned same-source reliability estimator.

The report includes oracle/feedback agreement, false-positive and
false-negative feedback rates, annotated noise rate, score gap, mean trust,
eligible-feedback rate, corrupted-feedback quarantine rate, and clean-feedback
quarantine rate. This separation is required before claiming robustness to
unreliable feedback.

### 5.2 PolicyShift benchmark

The deterministic enterprise-style stream keeps one refund-policy domain while
changing the hidden policy over three phases:

1. seven-day refund window;
2. expansion to fourteen days;
3. thirty-day premium exception while standard customers remain at fourteen.

The prompt exposes only customer tier and request day. Policy versions and both
labels remain outside the solver payload. Every sample belongs to exactly one
policy-role slice:

- `transition_case`: its correct decision changed at the current boundary;
- `protected`: its correct decision is invariant across all policy versions;
- `future_change_case`: it has not changed yet but will change at a later
  boundary, so adopting the future rule early is an error.

Deterministic noise flips arbitrary feedback, while targeted attack feedback
reinforces the superseded policy only on current transition cases.

PolicyShift reports changed-case success, old-rule leakage, invariant
retention, future-change success, premature-update rate, corrupted-feedback
following, and attack-following rates in addition to the standard stream
metrics.

Ordinary replay examples are restricted to the current detected regime.
Protected invariant examples may cross regime boundaries. Report
`shift_detection_events` separately from `domains_with_detected_shift`; the
former counts alarms, while the latter counts domains that experienced at least
one alarm.

## 6. Metric definitions

Let `s_t` be the stored first-pass primary score for episode `t`, `y_t` its
binary success flag, and `T` the stream length.

### 6.1 Overall and phase performance

The implementation reports:

\[
\text{MeanScore}=\frac{1}{T}\sum_{t=1}^{T}s_t,
\qquad
\text{SuccessRate}=\frac{1}{T}\sum_{t=1}^{T}\mathbb{1}[y_t].
\]

The same two quantities and sample count are computed separately for each
phase, preserving stream order.

### 6.2 Post-shift gain

For paired VERA and baseline streams and shift boundaries `B`, let `U` be the
union of the first `W` episode indices after every boundary. Overlapping
windows are deduplicated. The implemented metric is:

\[
\text{PostShiftGain}=\frac{1}{|U|}\sum_{t\in U}
\left(s_t^{\text{VERA}}-s_t^{\text{baseline}}\right).
\]

`post_shift_gain` defaults to `W = 20`. Phase transitions and explicit detected
shift events are both included by `infer_shift_indices`. For analysis, also
report known phase-boundary results separately from detector-triggered events;
otherwise false detector alarms can change the evaluation window.

### 6.3 AUAC

`area_under_adaptation_curve` uses normalized trapezoidal integration. Given
accuracy observations `a_i` at strictly increasing steps `x_i`:

\[
\text{AUAC}=\frac{1}{x_n-x_1}\sum_{i=1}^{n-1}
(x_{i+1}-x_i)\frac{a_i+a_{i+1}}{2}.
\]

With no explicit steps, `x_i = i`. The runner currently supplies raw
per-episode primary scores. For a paper-style learning curve, additionally
compute AUAC over preregistered rolling or checkpoint accuracies and state the
window/checkpoints.

### 6.4 Recovery steps

At a boundary `b`, the default target is
`recovery_fraction * mean(s_0, ..., s_(b-1))`. With rolling window `w`, recovery
is the smallest number of post-shift episodes consumed such that the most
recent full `w`-episode mean reaches the target. If the stream ends first, the
result is `N/A` (`None` in JSON), not zero.

The configured recovery fraction is `0.90`. The current stream summary uses a
five-episode recovery window; this window is a function argument rather than a
YAML field and must be reported if changed.

### 6.5 Cumulative regret

For comparator rewards `c_t`:

\[
R_T=\sum_{t=1}^{T}(c_t-s_t).
\]

The runner's default `c_t = 1`, so `cumulative_regret` is cumulative error for
scores bounded by one. When a paired baseline is supplied,
`cumulative_regret_vs_baseline` uses its per-sample score as `c_t`. Negative
terms are retained unless `clip_negative=True` is explicitly requested.

### 6.6 Backward transfer and forgetting

Let `A_(i,j)` be performance on a fixed held-out probe for domain `j` after
adapting through domain `i`, with `N` total domains and final row `N - 1`:

\[
\text{BWT}=\frac{1}{N-1}\sum_{j=0}^{N-2}(A_{N-1,j}-A_{j,j}),
\]

\[
\text{Forgetting}=\frac{1}{N-1}\sum_{j=0}^{N-2}
\left(\max_{i\in\{j,\ldots,N-1\}}A_{i,j}-A_{N-1,j}\right).
\]

`backward_transfer` and `forgetting` implement these formulas for an explicitly
provided performance matrix. The normal runner does not construct that matrix
automatically.

Held-out forward transfer should be reported as the paired frozen-memory gain
over the static agent on untouched domains. It must not include updates made
on the held-out domain itself.

### 6.7 Promotion precision

For promotion decisions `p_i` and independently measured realized gains `g_i`:

\[
\text{PromotionPrecision}=
\frac{\sum_i \mathbb{1}[p_i=1 \land g_i>0]}
{\sum_i \mathbb{1}[p_i=1]}.
\]

If no candidate is promoted, the implementation returns zero. When
`realized_gains` are omitted, it uses replay `mean_delta`; the current runner's
reported value is therefore **replay-estimated promotion precision**, not an
independent generalization estimate. A held-out audit must supply future or
untouched-domain gains before this metric supports a reliability claim.

### 6.8 Resource and latency metrics

Foreground `usage_metrics` reports logical task requests,
input/output/total tokens, USD,
tokens per episode, tokens and USD per success, mean latency, and linearly
interpolated p50/p95 latency. If `total_tokens` is absent, it uses input plus
output tokens. Always accompany these fields with total `costs.json` ledger
values so adaptation overhead is visible. Cached responses preserve token
metadata but have zero recorded cost and latency; disable or isolate the cache
for any latency or billed-cost claim.

Prefer Pareto plots or paired accuracy-at-budget tables over a single arbitrary
cost-weighted score.

## 7. Statistical analysis

### 7.1 Paired bootstrap

For a baseline and candidate evaluated on identical sample IDs, form
`delta_t = candidate_t - baseline_t`. The implemented API
`paired_bootstrap_ci(deltas, samples, confidence, seed)` resamples this delta
vector with replacement and returns a percentile interval for its mean.

The comparison CLI currently uses 2,000 bootstrap samples, 95% confidence, and
seed 42 through the function defaults. Promotion gates instead use
`evolution.bootstrap_samples` and `evolution.confidence_level`, with bootstrap
seed 42.

For the final report:

- pair methods by sample ID and seed;
- use at least 10,000 bootstrap resamples in the offline analysis if cost is
  negligible;
- report the mean paired difference, interval, and absolute percentage-point
  effect;
- with five repeated seeds, use a hierarchical or cluster bootstrap over seed
  and sample ID. The current helper is a one-level bootstrap and does not by
  itself account for repeated-seed clustering.

### 7.2 McNemar test

For binary success, also report the exact paired McNemar test using discordant
counts: samples solved only by VERA and samples solved only by the baseline.
Use an exact binomial version when discordant counts are small. McNemar is a
recommended offline analysis and is not currently implemented in EvoShift's
dependency-free statistics module.

Apply Holm correction across the preregistered primary baseline and ablation
comparisons. Statistical significance without a meaningful effect size, safe
protected slices, and acceptable cost is not sufficient for promotion or a
project claim.

## 8. Promotion gate and independent audit

`PromotionGate` computes paired candidate-minus-control deltas over the replay
buffer. A candidate is promoted only when every configured check passes:

1. replay count is at least `min_validation_examples`;
2. mean delta is at least `min_mean_gain`;
3. bootstrap lower bound is at least `min_ci_lower_bound`;
4. fraction of examples with negative delta is at most
   `max_regression_rate`;
5. mean regression on the protected mask is at most
   `max_protected_slice_regression`;
6. relative mean cost increase is at most `max_cost_increase_ratio`.

The full BBH configuration uses:

| Gate parameter | Full BBH value |
|---|---:|
| Replay window | 16 |
| Minimum validation examples | 8 |
| Bootstrap samples | 2,000 |
| Confidence | 0.95 |
| Minimum mean gain | 0.03 |
| Minimum CI lower bound | 0.00 |
| Maximum regression rate | 0.10 |
| Maximum protected mean regression | 0.02 |
| Maximum cost increase ratio | 0.30 |

Replay selection is deterministic: approximately two thirds are recent,
query-relevant historical episodes and up to one third are protected episodes.
When dollar usage is positive it is the cost signal; otherwise token count is
used. Protected phases are previously seen regression probes, not a held-out
test.

For the implemented whole-state audit, first run the static held-out control,
then use `evoshift audit --source-run ...` on the same held-out config and
compare the two run directories. The audit run records its source run, source
dataset hash, source state hash, target dataset hash, and `state_unchanged`
invariant. Audit scores are never passed to the critic, utility posterior,
memory writer, policy proposer, or promotion gate.

Candidate-level audit is stricter: freeze each promoted card and the final
policy, then run paired counterfactual inference on untouched samples with and
without that card. Record realized gain, harm rate, token delta, and agreement
with the replay decision. This per-card workflow is not automated yet and is
the missing evidence for held-out promotion precision and memory-utility
calibration.

## 9. Ablation matrix

Run the smallest matrix that identifies where the gain comes from. Every row
uses the same model, stream, seed list, and reporting protocol.

| Row | Variant | Current control | Question isolated |
|---|---|---|---|
| B0 | Static | `algorithm: static`, fresh isolated state | Does any adaptation help? |
| B1 | Self-Refine | `algorithm: self_refine` | Is within-task extra inference enough? |
| B2 | Unverified Reflexion | `algorithm: reflexion` | Does verification prevent harmful append-only memory? |
| V0 | Full VERA | `algorithm: evoshift` | Complete method |
| A1 | No slow policy evolution | `policy_evolution_enabled: false` | Contribution of policy-genome mutation |
| A2 | Historical rather than paired control | `paired_replay: false` | Value of paired replay under API stochasticity |
| A3 | No protected replay | `protected_phases: []` | Contribution to backward safety and forgetting |
| A4 | No UCB exploration | `policy.exploration_weight: 0` | Value of underused-card exploration |
| A5 | No utility term | `policy.utility_weight: 0` | Value of learned card utility |
| A6 | No MMR diversity | `policy.mmr_lambda: 1` | Value of redundancy suppression |
| A7 | BM25-only retrieval | relevance weight 1; utility/exploration 0; `mmr_lambda: 1` | Value of the full hybrid retriever |

`Reflexion` is a useful baseline but not a perfectly isolated “minus
verification” ablation because it also lacks slow policy evolution. A strict
verification-only ablation would require a new behavior toggle that promotes
all candidates while leaving the rest of VERA unchanged. Do not claim that the
current Reflexion row isolates verification completely.

Do not tune each ablation separately on the test stream. Freeze all shared
hyperparameters from meta-development and change only the named component.

## 10. Future public memory benchmarks

LongMemEval and LoCoMo are planned, public extensions for conversational
long-term memory. They should be separate tracks rather than merged with BBH:

- LongMemEval can test long-range information retention, temporal reasoning,
  abstention, and evidence retrieval over long histories.
- LoCoMo can test multi-session conversational memory and event/person
  consistency over time.

Before reporting either dataset, implement a pinned adapter, license and
revision manifest, official task-specific scorer, contamination statement, and
the same prequential label firewall. These benchmarks evaluate memory quality,
not the same distribution-shift construct as the BBH stream. Report their
metrics separately and do not average them into one “SOTA” number.

As of this protocol, EvoShift contains no dedicated LongMemEval or LoCoMo
adapter and makes no empirical claim on either dataset.

## 11. Reproducibility checklist

Every reported run must retain:

- `manifest.json`: git commit/dirty flag, model, algorithm, seed, config hash,
  and dataset hash;
- `resolved_config.yaml`: all provider, budget, evolution, shift, benchmark,
  evaluation, and policy values;
- `predictions.jsonl`: immutable first-pass episodes;
- `promotion_decisions.jsonl`: paired replay deltas and every gate result;
- `metrics.json`: foreground stream metrics;
- `costs.json`: uncached external-provider-call budget ledger;
- `summary.json`: final policy, active memories, and audit notes;
- paired comparison JSON/Markdown from `evoshift compare`.

Pin the provider model identifier and evaluation date. Closed API models can
change behind a stable name, so a later rerun is a replication, not necessarily
the same model snapshot.

## 12. SOTA claim red lines

Do not use “SOTA”, “state of the art”, or “outperforms the leaderboard” unless
all of the following are true:

- the dataset revision, official split, prompt/tool conditions, scorer, and
  resource rules exactly match the compared result;
- VERA is frozen before an official test split, or the comparison explicitly
  uses the same published online-adaptation protocol;
- the base model and available test-time compute are matched or the difference
  is made central to the comparison;
- all planned seeds and phases are reported with uncertainty;
- no main-test label or reference entered adaptation before first-pass scoring;
- a separate held-out audit confirms that replay-promoted memories generalize;
- total adaptation cost, not just foreground solver cost, is reported;
- the model/data contamination limitation is stated.

In particular, an agent that adapts after each public BBH answer is scored may
produce a valid **prequential online-learning result**, but that number is not
an official static BBH leaderboard score. A custom eight-subset, ordered stream
is not directly comparable to a published full-BBH aggregate. The defensible
claim for the MVP is a paired, same-backbone improvement on the declared
EvoShift-BBH stream, subject to confidence, regression, cost, and held-out
audit evidence.
